01
형성평가 (강별)

형성평가는 부담 없는 연습이다. 재응시 무제한, 즉시 피드백. 목표 정답률 80% 이상. 문항 유형: 객관식 · 상황판단(시나리오) · O/X · 짝맞추기(매칭)로 다양화.

0강 형성평가 — "출발선 정렬"

학습목표 매핑: (이해) 바이브코딩이 "코딩이 아니라 지시와 검증"임을 설명한다 · (적용) 도구 10종 설치·체크리스트 완료 · (적용) 본인 업무를 I/P/O로 기술한다. 블룸 분포: 기억·이해 70% / 적용 30%.

Q0-1 [객관식 | 블룸: 이해 | 난이도: 하]

이 과정이 정의하는 "바이브코딩"을 가장 정확히 설명한 것은?

A) 코드를 한 줄도 몰라도 되며, AI가 만든 결과는 자동으로 정확하므로 사람이 확인할 필요가 없다 B) 자연어로 하고 싶은 일을 지시해 결과물을 만들되, 사실·품질 검증은 사람이 한다 C) 개발자가 빠르게 코딩하기 위한 단축키와 자동완성 기법의 모음이다 D) 프로그래밍 언어를 문법부터 순서대로 암기해 직접 코드를 작성하는 학습법이다

정답: B 해설: 과정의 한 줄 정의는 "코딩하지 않고 자연어로 지시하며, 검증은 사람이 한다". 지시는 AI, 검증은 사람이라는 역할 분담이 핵심이다. 오답 피드백:

  • A 선택 시: (E) "검증할 필요가 없다"고 본 점이 문제입니다. (E) AI는 그럴듯한 허위(숫자·출처)를 만들 수 있어, 검증을 생략하면 잘못된 산출물이 그대로 나갑니다. (C) 과정 표어의 뒷부분 "검증은 사람이 한다"를 다시 확인하세요. — 0-1 오리엔테이션
  • C 선택 시: (E) 개발자용 코딩 보조로 오해했습니다. (E) 그러면 "코딩 무경험 전제"라는 이 과정 대상과 맞지 않습니다. (C) 바이브코딩은 코드를 짜는 게 아니라 자연어로 지시하는 방식임을 확인하세요.
  • D 선택 시: (E) 문법 암기 학습으로 오해했습니다. (E) 이 과정은 문법을 외우지 않습니다. (C) "코딩하지 않고 자연어로"가 출발점입니다.

Q0-2 [O/X | 블룸: 이해 | 난이도: 하]

사전과제로 요구되는 "본인 업무를 I/P/O(입력→처리→출력) 형식으로 적기"는, 나중에 4강에서 본인 업무를 자동화하는 미러링(복제·개조)의 재료로 쓰인다.

  • X 선택 시: (E) 사전과제를 단순 워밍업으로 보았습니다. (E) 그러면 4강에서 미러링할 소재가 없어 본인 업무 자동화가 막힙니다. (C) 사전과제는 버리는 게 아니라 4강까지 이어지는 부품임을 기억하세요. — 누적 부품 이월 지도

Q0-3 [상황판단 | 블룸: 적용 | 난이도: 중] ★ 안전수칙 필수

당신은 0강에서 Supabase 설정을 마쳤습니다. 조교에게 "설정 잘 됐나요?" 물어보려고 화면 전체를 스크린샷해 조별 단체 채팅방에 올리려 합니다. 그런데 그 화면에는 service_role 키(비밀키) 값이 그대로 보입니다. 가장 올바른 행동은?

A) 조원들끼리만 보는 방이니 그대로 올려도 안전하다 B) 키 값은 나중에 어차피 바뀌니 지금은 신경 쓰지 않고 올린다 C) service_role 등 비밀키가 보이는 부분을 가리거나 제외하고, 필요한 부분만 캡처해 올린다 D) 스크린샷 대신 키 값을 텍스트로 복사해 채팅방에 붙여넣으면 안전하다

정답: C 해설: 0강 안전수칙 — service_role 등 비밀키는 어디에도(스크린샷 포함) 올리지 않는다. 비밀키는 DB 전체를 제어할 수 있는 "마스터 키"라, 소규모 채팅방이라도 노출되면 유출로 간주해야 한다. 오답 피드백:

  • A 선택 시: (E) "우리끼리니까 괜찮다"는 판단이 위험합니다. (E) 채팅방은 캡처·전달·유출 경로가 많아 통제 불가입니다. (C) 방 크기와 무관하게 비밀키는 노출 금지입니다.
  • B 선택 시: (E) "곧 바뀐다"는 근거가 틀렸습니다. (E) 노출된 순간 이미 유출이며, 재발급 전까지 악용될 수 있습니다. (C) 노출 자체를 막는 게 원칙입니다.
  • D 선택 시: (E) 스크린샷만 위험하다고 오해했습니다. (E) 텍스트 붙여넣기도 동일한 노출입니다. (C) 형식과 무관하게 비밀키 값 자체를 공유하지 마세요.

0강에서 미리 완료해야 하는 준비물로 묶은 것 중, 이 과정이 요구하지 않는 것은?

Q1-1 [객관식 | 블룸: 이해 | 난이도: 하]

1강에서 배운 LLM 4종 지형도에 해당하는 조합은?

A) Claude · Word · Excel · PowerPoint B) Claude · GPT(ChatGPT) · Gemini · Grok C) GitHub · Vercel · Supabase · Node.js D) Chat · Cowork · Code · Console

정답: B 해설: LLM(대형 언어모델) 4종은 Claude / GPT / Gemini / Grok이다. 오답 피드백:

  • A 선택 시: (E) 오피스 프로그램과 혼동했습니다. (E) 이들은 LLM이 아닙니다. (C) LLM은 자연어로 대화·생성하는 AI 모델임을 확인하세요.
  • C 선택 시: (E) 배포 도구(GitHub·Vercel·Supabase)와 혼동했습니다. (E) 이들은 AI 모델이 아니라 코드 저장·배포·DB 도구입니다. (C) 1-2(LLM 지형도)와 1-5(배포 3종)를 구분하세요.
  • D 선택 시: (E) 2강의 Claude 3계층(chat/cowork/code)과 혼동했습니다. (E) 이는 LLM 종류가 아니라 Claude의 사용 층위입니다. (C) "4종 모델"과 "3계층 사용법"은 다른 개념입니다.

Q1-2 [상황판단 | 블룸: 적용 | 난이도: 중]

당신은 스켈레톤(반쯤 완성된 페이지 틀)을 받아 랜딩페이지를 만들고, 실제 인터넷 주소(URL)로 공개하려 합니다. 이 과정이 가르친 배포 흐름의 순서로 가장 올바른 것은?

A) Supabase에 코드를 올린다 → Vercel에서 DB를 만든다 → GitHub에서 주소를 받는다 B) 자연어로 스켈레톤을 채운다 → GitHub에 코드를 올린다 → Vercel로 배포해 URL을 얻는다 → Supabase에 폼 데이터를 저장한다 C) 먼저 URL을 구매한다 → 코드를 직접 손으로 작성한다 → 이메일로 파일을 보낸다 D) VS Code에서 페이지를 그림으로 그린다 → 스크린샷을 Vercel에 업로드한다

정답: B 해설: 1-4에서 자연어로 스켈레톤을 채우고, 1-5에서 GitHub(코드 저장) → Vercel(배포·URL 생성) → Supabase(폼 데이터 저장) 순으로 연결한다. 각 도구의 역할이 다르다: GitHub=저장, Vercel=배포, Supabase=데이터. 오답 피드백:

  • A 선택 시: (E) 도구 역할을 뒤섞었습니다. (E) Vercel은 DB를 만드는 곳이 아니고, 주소는 Vercel이 줍니다. (C) 저장(GitHub)→배포(Vercel)→데이터(Supabase) 역할을 다시 확인하세요. — 1-5
  • C 선택 시: (E) "코드를 손으로 작성"이 이 과정 방식과 반대입니다. (E) 바이브코딩은 자연어 지시로 코드를 생성합니다. (C) 원칙⓵ 백지 시작 금지 — 스켈레톤에서 출발합니다.
  • D 선택 시: (E) 페이지를 이미지로 오해했습니다. (E) 랜딩페이지는 그림이 아니라 실제 동작하는 웹페이지입니다. (C) 배포는 스크린샷 업로드가 아니라 코드 게시임을 확인하세요.

Q1-3 [상황판단 | 블룸: 분석 | 난이도: 중] ★ 안전수칙 필수 (anon vs service_role)

Supabase는 두 종류의 키를 줍니다: anon(공개용) 키와 service_role(비밀·전권) 키. 배포한 랜딩페이지 코드에 웹에 공개되어도 되는 키는 무엇이며, 그 이유로 옳은 것은?

A) service_role 키 — 전권이 있어 어떤 기능이든 되므로 편리하다 B) 두 키 모두 넣어야 페이지가 정상 동작한다 C) anon 키 — 제한된 권한만 있어 공개를 전제로 설계된 키이기 때문 D) 어떤 키도 페이지에 넣으면 안 되고, 매번 손으로 입력해야 한다

정답: C 해설: 1강 안전수칙 — anon 공개키만 페이지에, service_role 키는 절대 금지. anon은 애초에 브라우저 노출을 전제로 권한이 제한된 키이고, service_role은 DB 전권을 가진 마스터 키라 웹페이지(누구나 소스를 볼 수 있음)에 넣으면 즉시 유출된다. 오답 피드백:

  • A 선택 시: (E) "편리하다"를 기준으로 골랐습니다. (E) 전권 키를 공개 페이지에 넣으면 누구나 DB를 삭제·탈취할 수 있습니다. (C) 편리함이 아니라 "공개 전제 여부"로 판단하세요. anon만 공개 가능합니다.
  • B 선택 시: (E) 둘 다 필요하다고 오해했습니다. (E) service_role을 넣는 순간 전체 DB가 위험해집니다. (C) 공개 페이지에는 anon 하나면 됩니다.
  • D 선택 시: (E) 안전을 위해 아무 키도 안 넣는다고 판단했습니다. (E) anon 키가 없으면 페이지가 DB와 연결되지 않아 폼 저장이 안 됩니다. (C) anon은 넣어도 되는 공개키임을 구분하세요.

Q1-4 [O/X | 블룸: 적용 | 난이도: 하] ★ 안전수칙

랜딩페이지의 문의 폼을 예시로 채울 때, 실제 고객의 실명·전화번호·주민번호 같은 개인정보를 넣어 시연해도 된다.

정답: X (거짓) 해설: 1강 안전수칙 — 개인정보를 폼 예시에 넣지 않는다. 배포된 페이지는 공개되고 데이터가 Supabase에 저장되므로, 예시에는 "홍길동 / 010-0000-0000"처럼 가짜/더미 값만 쓴다. 오답 피드백:

  • O 선택 시: (E) 실제 개인정보를 예시로 써도 된다고 보았습니다. (E) 공개 배포 + DB 저장이라, 실개인정보를 넣으면 유출·법적 문제가 됩니다. (C) 예시는 항상 더미 데이터로만 채우세요.

Q1-5 [짝맞추기 | 블룸: 이해 | 난이도: 중]

1강에서 배포에 쓰는 3종 도구의 역할을 알맞게 연결하세요.

도구 역할
① GitHub ㉮ 코드를 실제 URL로 배포(공개)한다
② Vercel ㉯ 코드를 저장·버전관리하는 창고
③ Supabase ㉰ 폼 데이터·로그인·저장소(DB) 담당

정답: ① - ㉯, ② - ㉮, ③ - ㉰ 해설: GitHub=코드 창고(저장), Vercel=배포(URL 생성), Supabase=데이터베이스. 이 3개가 한 세트로 "저장→배포→데이터"를 이룬다. 오답 피드백:

  • ①과 ②를 바꾼 경우: (E) 저장소와 배포를 혼동했습니다. (E) GitHub은 주소를 만들지 않고, URL은 Vercel이 만듭니다. (C) "깃허브=창고, 버셀=배포"로 기억하세요.
  • ③을 다른 것과 바꾼 경우: (E) 데이터 담당을 놓쳤습니다. (E) 폼 저장이 어디로 가는지 모르면 데이터 흐름을 통제할 수 없습니다. (C) Supabase=DB(데이터·로그인·저장소)로 고정하세요.

  • D 선택 시: (E) 수집 결과를 무검증 신뢰했습니다. (E) 수집된 뉴스에 오류·허위가 섞일 수 있습니다. (C) 출처 없는 주장은 배제하고 교차검증을 거치세요.

Q4-3 [객관식 | 블룸: 평가 | 난이도: 중] ★ 필수 (루브릭 자기판정)

수료 루브릭 3기준은 실데이터 동작 · 결과 지향 · 재현성입니다. 다음 중 "결과 지향(⓶)" 기준을 통과한 사례는?

A) 하네스를 돌리니 "처리 완료"라는 응답 메시지가 떴다 B) 하네스를 돌리니 실제로 오늘자 뉴스 브리핑 카드 1장이 파일로 만들어졌다 C) 에이전트가 에러 없이 실행되었고 로그가 출력됐다 D) 같은 입력을 넣으니 매번 다른 형식의 응답이 나왔다

정답: B 해설: 기준⓶ 결과 지향 = "'응답이 있다'가 아니라 '결과가 만들어진다'". 브리핑 카드라는 실산출물이 생겨야 통과다. (참고: A·C는 "응답/실행"에 그침, D는 재현성⓷ 위반.) 오답 피드백:

  • A 선택 시: (E) "응답 메시지"를 결과로 착각했습니다. (E) 메시지만 뜨고 산출물이 없으면 업무에 쓸 것이 없습니다. (C) 기준⓶는 "만들어진 결과물"을 봅니다.
  • C 선택 시: (E) "에러 없이 실행"을 결과로 보았습니다. (E) 실행 성공과 결과물 생성은 다릅니다. (C) 로그가 아니라 산출물이 나왔는지 확인하세요.
  • D 선택 시: (E) 이는 결과 지향이 아니라 재현성(⓷) 실패 사례입니다. (E) 같은 입력에 매번 다른 결과면 신뢰할 수 없습니다. (C) 재현성 기준을 별도로 점검하세요.

Q4-4 [O/X | 블룸: 평가 | 난이도: 하] ★ 안전수칙

에이전트팀이 자동으로 브리핑을 만들어 주더라도, 대외로 내보내기 전 최종 사실·기밀 확인은 사람이 해야 한다.

정답: O (참) 해설: 4강 안전수칙 — 최종 확인은 사람 · 고객 식별정보/기밀 입력 금지. 자동화가 아무리 매끄러워도 마지막 게이트는 사람이며, 이것이 과정 전체의 표어("검증은 사람이 한다")와 일치한다. 오답 피드백:

총괄평가 (4강 캡스톤) — 수료 루브릭 3기준 판정

성격: 총괄평가(Summative). 학습 완료 후 성취를 측정한다. 형성평가와 달리 자기판정 + 안전 게이트 통과를 함께 요구한다. 합격 기준: 루브릭 3기준 모두 통과 + 안전 게이트 4항목 모두 통과 → 수료. 하나라도 미충족 시 30일 클리닉에서 보완 후 마무리. 목표 정답률/통과율: 총괄평가 70% 이상. 학습자에게 사전 공개한다(평가 전 루브릭을 보여준다 — 학습 방향 설정).

A. 수료 루브릭 (분석적 루브릭 — 3기준)

기준 확인 질문 ✅ 통과 (관찰 가능한 증거) ⚠️ 보완
⓵ 실데이터 동작 실제 본인/공통 업무 데이터로 동작하는가 더미가 아닌 실제 업무 데이터(예: 오늘자 뉴스, 본인 부서 실사례)로 하네스가 끝까지 실행됨 샘플/가짜 데이터에서만 돌고 실데이터에서 멈춤
⓶ 결과 지향 "응답이 있다"가 아니라 "결과가 만들어진다"인가 실행 후 사용 가능한 산출물(브리핑 카드·파일·게시물 등)이 생성됨 "완료" 메시지·로그만 있고 산출물 없음
⓷ 재현성 같은 입력 2회 실행 시 동일 품질인가 동일 입력으로 2회 실행 → 동등 품질·형식의 결과가 재현됨 실행마다 형식·품질이 들쭉날쭉함

수료 판정 규칙: ⓵·⓶·⓷ 모두 ✅ + 아래 안전 게이트 통과 = 수료 확정. 하나라도 ⚠️면 보완(30일 클리닉 마무리). 수료 증명: 배포된 데모 URL + 동작하는 하네스 산출 영상/기록.

B. 안전 게이트 체크리스트 (전 실습 공통 — 하나라도 위반 시 산출물 반려)

4강 하네스 제출 전, 아래 4항목을 학습자가 직접 ✅ 체크한다. 이는 0~4강 안전수칙의 종합 점검이다.

  • ① 비밀키 노출 0 — service_role 등 비밀키가 코드·페이지·스크린샷·채팅 어디에도 없다. 공개 페이지엔 anon 공개키만 사용했다. (0강·1강·3강)
  • ② 개인/고객정보 입력 0 — 실명·연락처·주민번호 등 고객 식별정보와 기밀을 프롬프트·폼 예시·MCP 입력에 넣지 않았다. (1강·2강·3강·4강)
  • ③ 사실 검증 수행 — 산출물의 숫자·법조항·출처를 사람이 1차 출처로 확인했다. 허위 숫자·법조항·출처 없는 주장이 없다. (2강·4강)
  • ④ 데이터 흐름·최종 확인 — MCP가 데이터를 어디로 보내는지 확인했고, 대외 산출 전 최종 확인을 사람이 했다. (3강·4강)

게이트 규칙: 4항목 전부 ✅여야 제출 유효. 하나라도 미충족 시 반려 후 재실행.

C. 총괄 판정 문항 (시나리오 기반 — 루브릭·안전 적용 능력 측정)

형성평가보다 상위(평가·창조) 수준. 각 문항은 루브릭 기준 또는 안전 게이트에 매핑된다.

S1 [상황판단 | 블룸: 평가 | 난이도: 상] — 매핑: 루브릭 ⓶ 결과 지향 + ⓷ 재현성

두 조가 하네스를 제출했습니다.

  • 가 조: 실행하면 "뉴스 5건 요약 완료"라고 뜨지만, 어디에도 요약 파일·카드가 저장돼 있지 않다.
  • 나 조: 실행하면 오늘자 뉴스 브리핑 카드가 파일로 생성되고, 같은 입력을 다시 넣어도 같은 형식·품질의 카드가 나온다.

루브릭 3기준에 비추어 옳은 판정은?

A) 가 조는 "완료" 메시지가 뜨므로 결과 지향(⓶)을 통과했다 B) 나 조는 산출물 생성(⓶)과 2회 재현(⓷)을 만족한다. 가 조는 산출물이 없어 ⓶ 미충족으로 보완 대상이다 C) 두 조 모두 실행이 되므로 자동 수료다 D) 가 조는 메시지가 더 빨리 떠서 재현성(⓷)이 우수하다

정답: B 해설: 결과 지향(⓶)은 "응답"이 아니라 "산출물"을 본다 → 가 조 미충족. 재현성(⓷)은 2회 동일 품질 → 나 조 충족. 나 조 수료 요건 근접, 가 조는 보완. 오답 피드백:

  • A 선택 시: (E) 메시지를 결과로 오인했습니다. (E) 산출물 없는 완료 메시지는 업무 가치가 0입니다. (C) ⓶는 만들어진 결과물로 판정합니다.
  • C 선택 시: (E) "실행됨"을 수료 기준으로 삼았습니다. (E) 실행과 결과·재현은 다른 층위입니다. (C) 3기준을 개별 확인하세요.
  • D 선택 시: (E) 속도를 재현성으로 착각했습니다. (E) 재현성은 빠름이 아니라 "같은 입력→같은 품질"입니다. (C) ⓷의 정의를 다시 보세요.

S2 [상황판단 | 블룸: 평가 | 난이도: 상] ★ 안전 게이트 종합 — 매핑: 게이트 ①②③④

수료 발표 직전, 한 조의 하네스에서 다음이 발견됐습니다. (1) 데모용 폼 예시에 실제 고객 이름·전화번호가 들어가 있음 (2) 요약 브리핑에 출처를 못 찾은 "업계 1위" 주장이 그대로 있음 (3) 코드에 API 키가 직접 적혀 있음

이 산출물에 대한 올바른 조치는?

A) 동작은 하므로 일단 수료시키고 문제는 나중에 고친다 B) (2)만 출처를 달면 나머지는 사소하므로 통과시킨다 C) 세 가지 모두 안전 게이트 위반(각각 ②·③·①)이므로 산출물을 반려하고, 개인정보 제거·출처 확인/삭제·키 분리 후 재실행한다 D) (1)(3)은 우리 조만 보는 것이니 괜찮고 (2)만 고친다

정답: C 해설: (1)은 게이트 ②(개인/고객정보 입력 0) 위반, (2)는 게이트 ③(사실 검증·출처 없는 주장 배제) 위반, (3)은 게이트 ①(비밀키 노출 0)/키 하드코딩 금지 위반. 안전 게이트는 하나라도 위반 시 반려 후 재실행이 규칙이다. 오답 피드백:

  • A 선택 시: (E) 동작을 안전보다 앞세웠습니다. (E) 개인정보·비밀키 노출은 동작 여부와 무관하게 즉시 위험입니다. (C) 안전 게이트는 수료의 선결 조건입니다.
  • B 선택 시: (E) 개인정보·키 노출을 "사소"로 보았습니다. (E) 이 둘은 법적·보안 사고로 직결됩니다. (C) 세 항목 모두 반드시 조치해야 합니다.

S3 [상황판단 | 블룸: 전이·창조 | 난이도: 상] — 매핑: 과정목표 4(미러링) + 루브릭 ⓵ 실데이터 동작
